# 播放引擎（player.js / mp4.js / mkv.js）和 mtcute

> 这是 [CLAUDE.md](../CLAUDE.md) 指过来的专题。上面「结论」是现在成立的；下面是前因后果和测量记录，按当时的样子留着，日期是那天的。

## 结论

- **mtcute 放在后台线程**：在主线程时解密校验每隔一两秒卡画面 300–850ms。后台线程用 `blob:` 地址起，凭证拼在脚本前面。
- **mtcute 的坑**：给它 wasm 字节会炸，要先 `await WebAssembly.compile()` 再交给它；下载没有背压，背压做在 `throttle` 钩子里；起点按 512KB 对齐（一次最多 512KB、不能跨 1MB）；`limit` 和 `offset` 别一起用。
- **连接作废**：电视把应用挂到后台一分钟以上，后台线程收不到心跳就作废连接（`Worker connection expired`）。tg.js 碰到就在同一个后台线程上重连、重试一次；页面卸载时不重连。
- **自己写 MP4 / MKV 解析**（mp4box 对长片太慢）：样本表存 TypedArray、二分找关键帧、自己拼 moof / mdat。2.6GB 长片起播 5.8 秒、跳到没缓冲的地方 0.64 秒。
- **按秒背压**，不按字节。音视频在文件里隔得远（4K 片子）就**分两路读**，拼好的段离播放头 90 秒以内才进 SourceBuffer（电视的音频 SourceBuffer 只有 ~8MB）。
- **三星的 MSE 不跨空档**：起点要落在音视频都有的地方。MKV 从 Cue 跳进去时第一帧音频常比视频关键帧晚几到一百多毫秒（mkvmerge），`alignStart` 把起点挪到晚的那个；刚打开时 `watchFirstFrame` 也跳开头的空档；播放中 `monitor` 跳。
- **跳转**：open GOP 的前导帧要丢、关键帧时长撑到下一个要放的帧；**先清旧缓冲、清完再挪播放头**。
- **高过 1088 的 H.264，Tizen 5.5 / 6.0 解不了**（竖屏 720x1280 这类，出画面前 `code=3`）：放不了，说清楚是这个原因、不当出事
  （这台电视放成过这么高的就不算这个原因）。Tizen 9 放得了。下面「2026-10-27」。
- H.264 级别写小了的改够（`Mp4.fixAvcLevel`）；当初以为它是 576x1280 那次 `code=3` 的原因，**不是** —— 是上面那条，见「2026-10-27」。
- avcC 头里的 profile 写成 0（`avc1.000004`）照 SPS 的改（`Mp4.fixAvcProfile`），不然 `isTypeSupported` 不认、一下都不试。
- **MKV 放到结尾 `ended` 可能不来**（最后一帧视频比音频早结束）：取完、离结尾不到一秒、卡 1.5 秒就当放完了，不然「下一集」等不来。
- **FLAC 音轨电视解不了**（`isTypeSupported` 说认，其实不解）：`audioOk` 当它放不了，有别的音轨换别的、没有就无声放（见 [音乐.md](音乐.md)）。DTS、TrueHD、ALAC 也解不了。
- 用 `-c copy` 从中间截的 MP4（编辑列表盖住几秒预滚、音频从负时间起）引擎不出画面 —— 还没改。
- **标着 video/mp4 的 MPEG-TS**（开头 `0x47`、每 188 / 192 字节一包）说是 MPEG-TS、不当出事；放它要 TS → fMP4 转封装，没做。见「2026-11-25」。
- **下载停了、重开也没字节**：不再无限重开，`stalled` 一级级升：重开 → 重新取消息（新的文件引用）→ 重建到存文件的 DC 的连接（mtcute `recreateDc`）
  → 再重开 → 说「下载停了」。第一次记文件在哪个 DC、主连接在哪个 DC。出画面之前也一样。`FILE_REFERENCE_EXPIRED` 拿到新引用后第一次马上重试。
- **停下了的这部（`fatal` 之后）计时器都停**（`sess.dead`）；读 SourceBuffer 的 `buffered` 一律 `sbBuffered()`（摘掉了的读了会抛）。
- 视频条目里 QuickTime 才有的 `fiel` / `chrm` 不进 init 段（`isoVideo`，和声音条目的 `isoAudio` 一样）；是不是它们让 Tizen 5.5 拒 init 段，没证实。

### 可行性探测的结果（2026-10-01 设备实测，参考机同 bilibili / 抖音那台）

**全链路通了**：扫码登录 → 全局搜索 → 边下边播 → 跳转，都在电视上跑起来了。

#### 坑

- **mtcute 0.32.3 给它 wasm 字节会炸**：`loadWasmBinary` 走 `WebAssembly.instantiate(bytes)` 拿回 `{module, instance}`，
  `initSync` 当成 Instance 用，抛「WebAssembly.Module(): Argument 0 must be a buffer source」。要先 `await WebAssembly.compile()`
  再把 Module 交给它（不能同步编译：Chromium 主线程不许同步编译 4KB 以上的模块）。桌面冒烟测试抓到的。
- **mtcute 的下载没有背压**：`downloadAsIterable` 的下载线程拿完一块就拿下一块，不管消费者读没读，暂停读取等于把整个文件
  往内存里堆。它留了 `throttle` 钩子（每块请求之前 await），背压做在那里。`limit` 参数和 `offset` 一起用是错的（算块数时
  把 limit 当成终点），只传 `offset` + `fileSize`、够了就 abort。
- **起点按 512KB 对齐**：Telegram 每次最多 512KB，且一次请求不能跨 1MB 边界。
- **mp4box 跳转音视频不对齐**：`seek(t, true)` 把视频退到关键帧、音频却落在 t（每个音频样本都是关键帧），两条轨起点差几秒，
  `video.buffered` 取交集，播放头落在空档里永远不动。拿第一次返回的关键帧时间再 seek 一次。
- **mp4box 对长片太慢**：每个样本一个 JS 对象（这部 ~93 万个）。解析 moov 4 秒、第一次 seek 9.5 秒、之后每 append 512KB
  常要 200–300ms 生成分段 —— 全在主线程，界面跟着卡。开头那 2.2–2.6 秒的卡顿多半也是它。**正式版自己写 MP4 解析：样本表
  存成 TypedArray、二分找关键帧、自己拼 moof/mdat。** 抖音那边短视频用 mp4box 没事，是因为样本少。
- 背压按字节（8MB 在途）在片头低码率时会多缓冲到 240 秒，正式版按秒数控制。
- `tizen package` 按 `<name>` 命名包，「TG 视频.wgt」带空格，`tizen install` 一行输出都没有就失败。deploy.sh 打完包改名。

### 正式版的播放引擎（2026-10-01 电视实测，《末代皇帝》219 分 2.6GB）

| | 探测版（mp4box，mtcute 在主线程） | 正式版 |
|---|---|---|
| 起播 | 9.5 秒 | **5.8 秒**（第一块 2.1，moov 6.4MB 到手 4.0，解析 0.41） |
| 解析 moov | 4.15 秒 | **0.41 秒**（32.8 万帧 + 61.6 万个音频样本，全是 TypedArray） |
| 跳到没缓冲的地方 | 主线程卡 9.5 秒 + 1.1 秒 | **0.64–0.69 秒** |
| 缓冲内 ±10 秒 | — | **0.10–0.13 秒** |
| 关掉重开、续播 | — | 4.5 秒（其中 moov 2.4 秒 —— 正式版有 moov 缓存） |
| 主线程长卡 | 4–9 秒 | 只剩解析 moov 那一下 0.4–0.5 秒 |

- **切到别的应用一分钟以上再回来，Telegram 全挂（`Worker connection expired`）**（10-02 电视上切去哔哩哔哩 6 分钟）：mtcute 的
  主线程端每 10 秒给后台线程发心跳，后台线程 60 秒收不到就作废这条连接；电视把应用挂到后台时主线程整个停住（那 6 分钟一行日志都没有），
  后台线程照跑。修法：`TGLib.create` 多给一个 `reconnect`，在同一个后台线程上新开一条连接（它支持多条，不用重连 Telegram、不用重新登录），
  tg.js 碰到这个错就重连、重试一次；下载流里碰到就重连后抛出，播放器自己重试。`test/worker-expire.mjs` 让主线程忙等 70 秒复现，
  重连 1ms、之后请求正常。**电视上还没验证。**
- **mtcute 必须放后台线程**：它在主线程时，数据成批到达那几秒每隔一两秒卡 300–850ms。加计时分清了：卡的时候我们自己
  拼分段（produce）最多 11ms，moov 还没到、produce 一行没跑的时候也照样卡 —— 是 mtcute 的解密校验。挪进 Worker 之后下载期间
  一次都不卡，跳转也从 0.87 → 0.64 秒。Worker 用 `blob:` 地址起（`file://` 页面不能从文件起），凭证拼在脚本前面；
  后台线程里可以同步编译 wasm（主线程不行）。会话存 IndexedDB，主线程版存的会话后台线程直接读得到（换过去没重新扫码）。
  `performance.memory` 在这台电视上一直不变（10MB），不能拿来判断 GC。
- **open GOP 跳转**：关键帧后面、解码顺序在后显示在前的「前导帧」参考上一个 GOP，跳过来时解出来是错的。桌面 Chrome
  （macOS 硬件解码）直接 `PIPELINE_ERROR_DECODE`。两处：跳转后丢掉前导帧、关键帧的时长撑到下一个要放的帧（解码时间断开超过
  两帧 MSE 就当成不连续，丢到下一个关键帧）；**先清空旧缓冲、清完再挪播放头** —— 反过来 Chrome 会先在旧缓冲里跳，旧缓冲里前导帧
  都在。缓冲内跳转遇到带前导帧的关键帧也改走重新取。中间怀疑过「硬件解码不认 CRA 开头」，离线用 ffmpeg + VideoToolbox 解三种
  变体全过，排除了。
- **视频的 edit list 偏移并进 trun v1 的有符号合成偏移**，首帧显示时间 = 0，和音频对齐；音频的（编码器预滚 20–50ms）不管。
  ffmpeg 读负的合成偏移会把整条轨往后挪一个常数，所以 test/check.mjs 只比相对时间。
- 跳转测量要防「清旧缓冲那几十毫秒 currentTime 还停在原处」：往回跳时原处比目标大，会被误判成已经出画面（报过一次 57ms）。
  判据是播放头落在目标之后 5 秒内。
- 关键帧平均 6 秒一个，±10 秒落在最近的关键帧上，实际可能是 +15。

### 音视频在文件里隔得远的片子：分两路读

《黑鹰坠落》4K HEVC（3.9GB，moov 在尾部）的布局：1 分钟处视频在 30.7MB、音频在 2.2MB；10 分钟 381.5MB / 51.0MB；72 分钟 2031MB / 491.6MB —— 越往后隔得越远（最远 2.9GB）。一路顺序读的后果：
- 续播 6:35 要先读过 176MB，**60 秒才出画面**；
- 音频越跑越前：读到视频之前音频已经攒了 6 分钟，**电视的音频 SourceBuffer 只有 ~8MB**，撑满报 QuotaExceeded；第一版「满了就停下载」直接死锁（视频永远到不了），看门狗重开也是同一个死结。
修法（player.js 的「路」lane）：打开时在 21 个时间点上量同一时刻音视频的偏移差，超过 16MB 就音视频各一路、各读各的位置，背压各算各的。之后同一处续播 **3 秒出画面、只下了 3MB**。另外：拼好的段先攒在内存里、离播放头 90 秒以内才进 SourceBuffer；QuotaExceeded 时只缩这条轨的提前量，不再挡下载。
桌面上用 `test/skew.mjs` 把普通测试片重排成同样的布局来测。

### 诊断日志里别人电视的问题（2026-10-26）

- **一台 Tizen 9，1.1.7：续播 mkvmerge 封装的 MKV 六次都 90 秒没画面；播放中每次跳转先卡 1–2.5 秒再「跳过空档」**。从 Cue 跳进去，
  拆出来的第一帧音频比视频关键帧晚 6–120ms（mkvmerge 把跨过关键帧的那帧音频放在上一个 Cluster），播放头放在关键帧上就落在交集的空档里，
  三星的 MSE 不跨。播放中的 monitor 会跳，刚打开时没人跳。修：`takeMkv` 拿到两条轨的第一帧后起点挪到晚的那个（`alignStart`，日志
  「音频比视频晚 Nms 开始，起点挪到 …」）；`watchFirstFrame` 里也跳开头的空档（交集攒够半秒、6 秒以内）。本地 mkvmerge 测试片续播
  就是晚 6ms；音频晚 5 秒的片子（我截 README 片段时撞上的那种）以前永远卡住，现在 0.18 秒出画面。
- **一台 Tizen 6.0，1.1.6：一部 576x1280 60fps 的竖屏 MP4，出画面前 `Player error code=3`**。文件里 H.264 写的是 Level 1.3
  （一帧最多 396 个宏块，这片 2880 个）。推测三星的硬件解码器按级别分配资源（可信度中低：这也是诊断日志里第一次有 Tizen 6.0 放片子）。
  修：帧大小超出写的级别时，avcC 和 SPS 的 level_idc 原地改成够用的一级（`Mp4.fixAvcLevel`，按 60fps 算），MP4 和 MKV 都走；日志
  「H.264 级别 1.3 → 3.2」。改过的 fMP4 ffmpeg 解得了。**这个推测错了**，见下面「2026-10-27」：级别改够了照样 code=3，原因是画面高。
- ALAC（Apple 无损）：那份日志来自别人改过的构建（有我们没有的「播放音频」）。电视上没有 ALAC 的解码路径（MSE、WebCodecs 都没有），
  提示改成「Apple 无损（ALAC）音频电视解不了」。
- 顺带：换片后旧会话的 `T.wait` / `T.retry` 计时器还会 `pumpSb`，SourceBuffer 已经摘了（「removed from the parent media source」），
  `pumpSb` 先看 T 还在不在当前会话；页面卸载时下载流里碰到连接作废不再重连；一次失败只报一次（以前「90 秒没出画面」后面紧跟「timeout」，
  出事记两回）；90 秒放弃时日志写 readyState、各轨缓冲、收了多少、最后一个字节多久前、队列。
- **MKV 放到结尾不报「放完了」**（桌面引擎测试一直是「播完=false」，以前没人看）：最后一帧视频比音频早结束几十毫秒，endOfStream 之后
  停在视频最后一帧上、`ended` 不来，「下一集」就等不来。整部片取完、离结尾不到一秒、卡住 1.5 秒 → 当放完了（之后不再报缓冲，往回跳重新计）。

### 诊断日志里别人电视的问题（2026-10-27）

- **高过 1088 的 H.264 在 Tizen 5.5 / 6.0 上解不了**。1.2.3 的五份上传（一台 Tizen 5.5、两台 Tizen 6.0）加上 10-25 那台 Tizen 6.0：
  高过 1088 的 H.264 **十四次全是出画面前 `code=3`**（632x1280、720x1280、720x1166、720x1138、970x1280、1242x1280，Baseline / Main / High
  都有），不高于 1088 的**十次全成**（848x464、480x860、1080x1080、1280x814、640x352，还有 608x1080 的 H.265）。看的是高、不是像素数：
  720x1166 失败、1080x1080 成功。一台 Tizen 9 放 720x1280 照常。抖音那边一台 Tizen 6.5 的竖屏 1080x1920 H.264 也一样，而同一台电视
  竖屏 1088x1920 的 H.265 直播放得了 —— 卡的是 H.264 解码器。**10-26 改的级别不是原因**：级别改够（日志里「1.3 → 3.2」）的那部照样 code=3。
  修：没出画面就 code=3、视频轨是高过 1088 的 H.264、这台电视没放成过这么高的（`tg.h264tall`，出画面后走了 2 秒才算）—— 屏幕上说
  「这台电视解不了高度超过 1080 的 H.264 视频（这部是 720x1280）」，不放留 issue 的码、不当出事。片子只有一个文件，放不了就是放不了；
  **Telegram 给大视频另外转好的清晰度**（`messageMediaDocument.alt_documents`）要是有矮一档的，那些电视就能改放它 —— 先在「播放」那行
  记下每部片的备选清晰度（「备选清晰度 720x1280 h264 12MB / …」），看别人电视上的片子有没有再做。参考机的账号（`--legacy` 那步顺带数）：
  一个电影频道 40 部里 3 部有，例如 1280x706 的有 1280x704、856x472 两档，各一份 h264、一份 av01（另有几份没有视频属性的，0x0）——
  读的路径（`m.raw.media.altDocuments`）是通的，矮一档的 H.264 Telegram 确实会给。下载它要原始位置 + `dcId`（`downloadAsIterable` 收）。
- **`avc1.000004` 打不开**（一台 Tizen 9）：avcC 头里 profile 写成 0、级别写成 4，`isTypeSupported` 不认这个字符串，一下都没试就
  「Video avc1.000004 can't be played」；同一个来源里 `avc1.4d0004`（级别一样写错）的照常放。修：profile 不是 H.264 有的值时照 SPS 改
  avcC 头（`Mp4.fixAvcProfile`；SPS 里也不对就写 Main），**SPS 不动** —— profile_idc 决定 SPS 后面有没有色度那几个字段。日志
  「avcC 的 profile 0 → 100」。把 a_h264_fast.mp4 的 avcC 改成 profile 0、级别 4 过 test/check.mjs：读成 `avc1.640004`，ffmpeg 解得了。
- **ALAC 的 m4a 放音乐时只报 DEMUXER_ERROR**（一台老电视，Chromium 55）：见 [音乐.md](音乐.md)。
- 那台 Tizen 9 手动传了一份：放了两部带内嵌 tx3g 字幕的电影，来回换了几次字幕就传上来了 —— 多半想说字幕，可日志里没有「字幕出没出来」
  那一行，看不出是什么。


## `CHUNK_DEMUXER_ERROR_APPEND_FAILED`：还没分开（2026-10-28 诊断日志）

两台 Tizen 9 各一部（`avc1.640028 1746x1080`、`hvc1.1.6.L123.B0 1926x1080`，moov 都在文件尾，宽度都怪、B0 约束字节和 0.5 秒交错像苹果编码器写的），
同一秒里 `SourceBuffer error video…`、`SourceBuffer error audio…`、`播放器出错 code=4 …`；两台紧接着放同编码的别的片子都好 —— 不是解码器，
是 Chromium 的 MP4 解析器拒收。疑点是原样拷进 init 段的 stsd，但秒级时间分不清坏的是 init 段还是第一段。
现在 `SourceBuffer error` 那行带「正在进的是 init 段还是 t=… 那段、之前进成几次」和 stsd 的样子（版本、条目数、条目类型、里面的盒子）。
下一份就分得开；是 stsd 的话，出画面前用合成的 stsd（只放 avcC / hvcC、esds）重开一次是现成的判别实验（mkv.js 的 `visual()` / `audio()` 能用）。

**⟶ 2026-11-14 分开了：是声音条目的写法。** 11-01…13 的上传里五台电视（越南 Tizen 6.0、智利 5.5、台湾 6.5、泰国 6.5，加上 10-28
那两台 Tizen 9）init 段一进去就 `stream parsing failed`，`stsdNote` 一律是 `mp4a[wave]` / `mp4a[wave,chan]`：QuickTime 写法的声音条目
（version 1 / 2 多出 16 / 36 字节，esds 包在 `wave` 里），苹果的编码器、手机录的片子都是这样。**桌面 Chromium 复现得一模一样**
（`test/media/g_qt_wave.mov`，原样拷 → `CHUNK_DEMUXER_ERROR_APPEND_FAILED: RunSegmentParserLoop: stream parsing failed`）。
`mp4.js` 的 `isoAudio()` 写 init 段前把这种条目改成 ISO 的样子：version 0、esds 从 wave 里拿出来、`chan` 之类 QuickTime 才有的盒子不要；
codecs 也去 wave 里找 esds（原来找不到就当 `mp4a.40.2`，HE-AAC 会标错）。同一处顺带改 Opus：条目里的声道数和 `dOps` 对不上时照 `dOps`
（11-08 一台 Tizen 9：「Opus AudioSampleEntry sample rate mismatches OpusSpecificBox STREAMINFO channel count」，比的其实是声道数）。
已经是 ISO 写法、对得上的原样拷，一个字节不动。`test/check.mjs` 卡着「音频 init 段必须是 ISO 写法」，两部测试片的生成命令在它头上；
`deploy.sh --samples` 在电视上放这两部（11-14 参考机：都出画面，3–4 秒）。

## 诊断日志里别人电视的问题（2026-11-25）

1.2.9 之后的上传里挑出来的几件（1.3.0 / 1.4.0 是别人改的版本，不算）：

- **MPEG-TS 冒充 MP4**：五份「不认识的文件格式」都是 `47401110 0042f025 0001c100 00ff01ff`（Tizen 6.5–10，357 MB–1.5 GB，类型都写着
  `video/mp4`、多半扩展名也是 .mp4）—— 这是 ffmpeg 写的 TS 的第一包（PID 0x11，SDT）。以前说「不认识」、放 issue 码、当出事传。
  现在 `findMoov` 开头不像盒子时先看是不是 TS（0 和 188、376 处都是 `0x47`；或者 M2TS 的 4 和 196），是就说「这个文件其实是 MPEG-TS 格式
  （不是真的 MP4），这个应用放不了这种格式」，`knownErr`。**没做播放**：TS 要转成 fMP4 才进得了 MSE（电视的 MSE 认不认 `video/mp2t` 没量过），
  hls.js 里有转封装器，可它要的是 HLS 的分段表（每段多长），一个几百 MB 的整文件没有，按大小均分猜时长的话跳转全是错的 —— 不是「现成的就能用」。
  桌面 `test/player.html?f=media/t_ts_as.mp4`、`deploy.sh --samples` 各一步（生成命令在 player.html 头上）。
- **出错之后的 js 错误**：两台电视（11-15 Tizen 9，High 10 的 H.264；11-24 Tizen 10，挂起醒来 `PIPELINE_ERROR_INITIALIZATION_FAILED`）`fatal()` 已经
  说清楚了，接着 `Failed to read the 'buffered' property from 'SourceBuffer': This SourceBuffer has been removed` @player.js:1028 —— 媒体元素出错后
  MediaSource 被关、SourceBuffer 被摘掉，`watchFirstFrame` 的计时器只看 `S !== sess`，第 90 秒照样去 `api.debug()` 读 `buffered`，抛在计时器里，
  一次说清楚了的失败变成「js 错误」出事上传。现在 `watchFirstFrame`、`monitor` 都看 `sess.dead`；`api.debug()` / `evict` 读 `buffered` 走 `sbBuffered()`
  （读不到写「摘掉了」）。桌面 `player.html?fatal=1`（出画面前让媒体元素出错、摘掉 MediaSource，等 95 秒）：改之前第 90 秒抛这个错，改之后 0 个。
- **下载卡死、只会重开**：11-24 一台 Tizen 10（下载本来就只有 0.1 MB/s）挂起醒来之后，`卡了 20 秒、字节也停了 … 重开` 33 次，每次一个字节都没有，
  同一时间来源列表照样刷得出来（主连接在答话）。之后电视又挂起一次，醒来时连接作废、重连，字节才回来；后来另一次「90 秒没出画面」也是收了 0.0MB。
  重开 = 同一个数据源再要一遍；`entry.js` 的重连只换 port，后台线程里到各个 DC 的连接是同一组 —— 到存这个文件的 DC 的下载连接要是卡死了，
  要多少遍都一样。**是不是这个原因没证实**，所以做成一级级升、每一步都记：
  `stalled(sess, t, why)`：「上次重开之后一个字节都没来」连着算次数 —— 0 照旧重开；1 数据源 `recover(1)` 重新取这条消息（新的文件引用）再重开；
  2 `recover(2)` 重建到存这个文件的 DC 的连接（`client.recreateDc(doc.dcId)`：mtcute 自己碰到 `MTPROTO_CLUSTER_INVALID` 也这么做，config 先刷一次，
  那个 DC 的主连接、下载连接一起拆了重连；文件就在主 DC 上的话主连接也跟着重来）再重开；3 再重开一次；4 不试了，屏幕上「下载停了：N 秒一个字节都没收到，
  重连过也一样…」，当出事（原因还不知道）。每步 15 秒没回就当没成、照样重开。第一次记一行 `这部片子：文件在 DC4，主连接在 DC2（下载走另一组连接）`；
  字节回来了记 `字节又来了：连着 N 次重开没字节，最后一步是…` —— 下一份就知道是哪一步管用、是不是总在非主 DC 上。
  出画面之前（`watchFirstFrame`）也走同一条：20 秒没字节、前方没攒够就升（90 秒的总限照旧）。**前方已经拼好 30 秒以上的**不算「下不来」
  （字节停着是因为够了 —— 见下一条），只重开、记 readyState 和各轨缓冲。`recreateDc` 走的是 TelegramClient → port → 后台线程，
  两份 mtcute（正常的、老电视的）都有，不用换壳。桌面 `player.html?stall=2`（跳到一半同时断流，`recover(2)` 之后解开）、`stall=0`（一直断，约 100 秒后放弃）。
- **暂停之后接着放，画面不走**（11-21 一台 Tizen 5.5，三次）：暂停了几分钟（这段时间前方攒着 60–75 秒、不再下载），按了接着放，播放头不动，
  20 秒后监视「重开」才好。推测和暂停久了有关，没证实，**只加了日志**：接着放的那一刻和 2 秒后的播放头、readyState、各轨缓冲、前方、最后一个字节
  多久前（`接着放（暂停了 N 秒）：…`，暂停 5 秒以内又走了的不记）；监视重开时写明前方还有多少、readyState、离按接着放多久。
  分得开「数据在、解码器不走」和「缓冲被清掉了」。`deploy.sh --samples` 里一部片子暂停 6 秒再放，3 秒内要走（参考机上量的是对照）。
- **`fiel` / `chrm`**：11-14 一台 Tizen 5.5，`avc1[avcC,fiel,chrm,pasp]` 的片子（声音条目 `mp4a[wave]`，已经改写成 ISO）两个 SourceBuffer 都在
  init 段上出错，`Append: stream parsing failed. Data size=695`。按我们的 init 段算，这个大小对得上视频那条（640x360 的测试片视频 init 675–693 字节，
  声音改写后 ~600）。`fiel`（场序）、`chrm` 是 QuickTime 才有的盒子，ISO 里没有，解码用不着 —— **中等把握**是它们，现在 `isoVideo` 去掉
  （`stsdNote` 写「去掉了 QuickTime 才有的 fiel、chrm」），别的子盒子原样留着。再出错时 `SourceBuffer error` 那行写着正在进的 init 段多少字节、
  `fatal` 那行写各轨 init 段的字节数。`test/check.mjs` 卡着视频 init 段里没有这两个（`c_hevc.mp4` 带 `fiel`；`chrm` 是把它改名造的）。
  Telegram 另外转好的清晰度（`alts`，这部有 1280x720 h264 一档）**没接**：mtcute 的包没把 Document 解析暴露出来，要自己拼原始的
  `inputDocumentFileLocation`、自己管它的文件引用过期 —— 新的一条下载路，电视上验证不了之前不做。
- **`FILE_REFERENCE_EXPIRED` 等 2 秒**：差不多每次开播第一个请求都是它（列表里的消息取得早，文件引用过期了），tg.js 当场重新取消息、拿到新引用，
  播放器却照样「2 秒后接着取」。现在数据源把错误标上 `freshRef`，第一次马上接着取（日志「拿到了新的文件引用，马上从 … 接着取」）。
