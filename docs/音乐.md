# 音乐（music.js / flac.js）

> 这是 [CLAUDE.md](../CLAUDE.md) 指过来的专题。上面「结论」是现在成立的；下面是前因后果和测量记录。

## 结论

- 来自 issue #3（「Telegram Music」，2026-10-25）。做成这个应用里的一部分，不另出一个应用：登录、来源栏共用。
- **混排**：Telegram 的「音乐」筛选（`inputMessagesFilterMusic`，带歌名 / 歌手属性的音频文件，不含语音）是 `TG.videos` 合并的第三路；
  只有歌的频道也进来源栏（`videoCount` 视频、当文件发的视频都没有时再问音乐）；搜索也搜。
- **放法：整首下下来，做成 `blob:` 交给 `<audio>`**。电视自己的播放器对 blob 的 MP3 / M4A / Opus / WAV 都放得了、跳得动；网上的 MP4 给
  `video.src` 却不可靠（见 [网页链接.md](网页链接.md)），所以不走「直接给地址」。放着这首就把下一首下好，内存里最多留 3 首。
- **FLAC 电视解不了**，哪条路都不行（下面的表）。音乐里的 FLAC 用 `flac.js` 自己解：边下边在后台线程里解成 16 位 PCM，拼成 WAV 再交给 `<audio>`。
  电视上解码约实时的 21 倍：3 分钟 CD 音质（18MB）下完又等 6.6 秒，从按键到出声 10 秒；之后的歌预先下好、解好。
- 视频里的 FLAC 音轨（MKV / MP4）在电视上当放不了（player.js 的 `audioOk`），不然会一直卡在「正在打开」。
- 界面：卡片是方形专辑图（Telegram 给的缩略图）放在同一张图缩小拉伸的底上；音乐画面左封面右歌名、歌手、来自哪个群、下一首；
  确认暂停、←→ 10 秒、↑↓（遥控器的上一曲 / 下一曲）换歌、返回回列表**接着放**（卡片上标「♪ 正在放」，点它回到画面不重放）、停止键停。
  放视频时歌停；切到别的应用时暂停。
- 放不起来也不报错的（以前的 FLAC 就是这样）12 秒不走算放不了，3 秒后放下一首；连着 5 首放不了就停。
- **有的电视 `<audio>` 连 MP3 / M4A 都不收**（11 月诊断日志：Tizen 10 上每一首都是 `DECODER_ERROR_NOT_SUPPORTED`，Tizen 6.0 的 MP3、
  Tizen 5.5 的 M4A 是 `Format error`；参考机 Tizen 9 放得了）。`<audio>` 报 error 4 就改用 Web Audio：WAV 读 PCM（`pcmPlayer`），
  别的用 `decodeAudioData` 整首解成 AudioBuffer（`bufPlayer`）；8 分钟以上的不解（内存），说清楚、不当出事。电视上解不解得了还没验证，
  日志里成了是「改用 Web Audio 放起来了」、没成是「Web Audio 也放不了」。见「<audio> 不收 MP3 / M4A」。
- **ALAC（Apple 无损）的 m4a 电视解不了**（2026-10-27 诊断日志：一串 40 首里的一首 68MB、5 分半，`<audio>` 只报
  `DEMUXER_ERROR_NO_SUPPORTED_STREAMS`，屏幕上是这句原话、还当出事传了上来）。app 下的时候看 moov 里的音轨（`m4aProblem`，用 mp4.js 的
  `parseMoov`），解不了就说「Apple 无损（ALAC）音频电视解不了」、3 秒后放下一首，不当出事；moov 在开头的头两块（1MB）到了就知道、不用下完，
  在末尾的下完才知道。要放的话得像 FLAC 那样自己解（ALAC 有开源解码器），还没做。
- **还没做**：离开应用后台播放（Tizen 的网页应用挂到后台就停）；随机 / 单曲循环；歌词。

## 电视怎么放音频文件（2026-10-26，`deploy.sh --music`，参考机 Tizen 9）

测试文件在这台电脑上（`test/media/music/`，`test/serve.mjs` 给），电视从局域网取。

| | `<audio>` + blob | `<audio>` + http 地址 | 跳到中间 |
|---|---|---|---|
| MP3 | ✓（下载完 0.5 秒出声） | ✓ | ✓ |
| M4A（AAC） | ✓ | ✓ | ✓ |
| Opus（OGG） | ✓ | ✓ | ✓ |
| WAV | ✓ | ✓ | ✓ |
| FLAC | ✗ 不报错、播放头不动 | ✗ | — |
| FLAC 装进 MP4 | ✗ | ✗ | — |

`canPlayType` 对 FLAC 说 probably。再用 MSE 对照（整个分段 MP4 一次 append）：

| MSE | 结果 |
|---|---|
| AAC，只有音频 | ✓ readyState 4 |
| AAC + 640x360 黑画面 | ✓ |
| FLAC，只有音频 | ✗ 数据全进去了（0–40 秒），readyState 停在 1 |
| FLAC + 640x360 黑画面 | ✗ 一样 |

`isTypeSupported('audio/mp4; codecs="flac"')` 是 true。所以不是「只有音频」的问题，是这台电视根本不解 FLAC。
（第一次配视频用的是 64x64 的黑画面，连 AAC 那个对照都出错、MediaSource 被关 —— 硬件解码器不收这么小的画面。）

## flac.js

按 RFC 9639 写：帧头、CONSTANT / VERBATIM / FIXED / LPC 子帧、Rice / Rice2 余数（含 escape）、wasted bits、三种声道还原。
16 位以上的右移成 16 位（和 ffmpeg 解成 s16 一样，不加抖动），以下的左移；采样率、声道数照原样。不校验 CRC、MD5。
LPC 用浮点累加（系数乘样本最多 2^40，32 阶加起来不到 2^46，2^53 以内是准的），再除以 2^shift 向下取整。
字节不够时从帧头重来，帧头不对往后找下一个 0xFFF8 / 0xFFF9。STREAMINFO 写了最大帧长就攒够它再解，没写攒 1MB。

后台线程的脚本是 `core` 函数的源码拼上收发消息的几行，用 `blob:` 地址起（电视上页面是 `file://`），所以 `core` 不能引用外面的东西。

`test/check-flac.mjs` 用 ffmpeg 生成 13 种（压缩级别 0 / 5 / 12、24 位、单声道、三种声道还原、只用固定预测、帧长 1152、6 声道、很小的音量），
解出来的 PCM 和 ffmpeg 解的逐字节一样；桌面上 100–200 倍速。

## 自测

## 50 MB 的 WAV 报 Format error（2026-10-28 诊断日志，还没分开）

一台 Tizen 6.0：一首 FLAC 解成 50.0 MB 的 WAV（按大小是 48kHz 立体声 16 位，源多半是 24 位），`audio error 4 MEDIA_ELEMENT_ERROR: Format error`。
WAV 头没问题。放成过的 WAV 只有参考机和一台 Chromium 55，都不到 16 MB。分不开「这代电视不认 WAV」和「blob 太大」。
现在 `audio error` 那行带 blob 的类型和 `canPlayType` 的答案；空串就是不认 WAV，`maybe` 而报错就更像大小。退路（被拒时改用 Web Audio 放）等分开了再做。

**⟶ 2026-11-14 像是大小**：越南一台 Tizen 6.0 连着三首 FLAC 解成 42.0 / 50.4 / 51.7 MB 的 WAV，都是 `Format error（audio/wav canPlayType=maybe）`
—— `maybe` 而报错，照上面的判据更像 blob 太大，不是这代电视不认 WAV。退路（被拒时改用 Web Audio 放，或者切成小块）还没做。

**⟶ 2026-11-14 做了退路（1.2.8）**：FLAC 解出来的 WAV `<audio>` 报错，就从下好的 blob 里读出 16 位 PCM，用 Web Audio 自己放
（`music.js` 的 `pcmPlayer`）：PCM 一直是那份 Int16Array，每次只把前面 5 秒变成 AudioBuffer、首尾相接排在 AudioContext 的时间轴上
（无缝，提前排 7.5 秒）；暂停 = `suspend`，跳转 = 停掉从那里重排，时间 = 起点 + 走过的 `currentTime`。日志 `改用 Web Audio 放：…`。
参考机和桌面都不拒 WAV，所以靠 `Music.test.rejectWav` 假装拒：`deploy.sh --music` 里那首 3 分钟的 FLAC 走一遍出声、暂停、接着放、快进，
`test/ui-emu.mjs`（ONLY=music）在桌面上也走一遍。越南那台电视上真拒的时候走不走得通，等它下一份日志。

## `<audio>` 不收 MP3 / M4A（2026-11 诊断日志，11-25 做了退路，电视上还没验证）

- 现象：两台 Tizen 10 上每一首 MP3（4–10 MB、3–5 分钟）都是 `audio error 4 DECODER_ERROR_NOT_SUPPORTED（audio/mpeg canPlayType=probably）`，
  M4A 是同一个错（`audio/mp4 canPlayType=maybe`）；一台 Tizen 6.0 的 MP3、一台 Tizen 5.5 的 M4A 是
  `MEDIA_ELEMENT_ERROR: Format error`。下载完、做成 blob 的那一秒就报，和放过视频没关系（有一台登录完第一件事就是放歌）。
  同样的放法在参考机（Tizen 9）上 MP3 / M4A / Opus / WAV 都行（上面的表）。这几台电视放视频没问题 —— 视频的声音走 MSE（AAC 解得了），
  不走 `<audio>` 自己的那条路。为什么 `<audio>` 不收，没查清。
- 退路：`<audio>` 报 error 4（不收这份）、下好的 blob 还在，就改用 Web Audio。`decodeAudioData` 是浏览器自己的软件解码（不经电视的播放器），
  整首解成 32 位浮点的 AudioBuffer，一个 AudioBufferSourceNode 放（`bufPlayer`：暂停 = `suspend`，跳转 = 停掉、从那里重放）。
  解出来 44.1kHz 立体声一分钟 21 MB，引擎解的时候还要多一两份，所以 **8 分钟以上的不解**（`DECODE_MAX_SEC`），屏幕上说「改用软件解码只能放
  8 分钟以内的」、不当出事；Telegram 没给时长的按 128kbps 估。WAV 那条（FLAC 解出来的大 WAV）照旧读 PCM、`pcmPlayer` 一段段放。
- 日志：成了一行 `<audio> 不收这首 MP3（audio error 4 …），改用 Web Audio 放起来了：decodeAudioData 1234ms，2 声道 48000Hz，解出来 92 MB，
  252 秒（9.6MB）`；没成一行 `… Web Audio 也放不了（…ms，…MB）：EncodingError …`，屏幕上是原来那句加上「Web Audio 也放不了」，当出事传上来
  —— 下一份就知道这些电视的 `decodeAudioData` 解不解得了 MP3 / AAC、要多久。
- 顺手：`<audio>` 不收的时候先来 error 事件、再是 `play()` 的 `NotSupportedError`，以前两个都报「放不了」，每首记两次，「连着 5 首放不了就停」
  按两倍数（两首半就停了）。现在那一下归 error 事件管。改用 Web Audio 的时候 `token` 换一轮，`<audio>` 那边迟到的回调对不上、不会把
  正在放的那首当成放不了跳走（1.2.8 的 WAV 退路有这个隐患：`play()` 的拒绝在 error 之后到，就会 3 秒后跳下一首）。
- 自测：`Music.test.reject(["mp3", "m4a"])` 让 `<audio>` 假装不收（原来的 `rejectWav` 并进来了，`"wav"` 是 FLAC 解出来的那种）。
  `deploy.sh --music` 多了四步：MP3、M4A 改用 Web Audio 解码放起来，MP3 那首暂停、接着放、快进，20 分钟的说太长；
  `ONLY=music node test/ui-emu.mjs` 在桌面上走 MP3、M4A 两首。参考机 Tizen 9 的 `decodeAudioData` 解不解得了，这一步就量出来了。
